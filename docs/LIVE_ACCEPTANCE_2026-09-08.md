## 升级空间

### 优先 1：同一浏览器的统一安全状态

问题：Git、Harness 或另一隔离安装各自配置不同 runtime home 时，即使连的是同一浏览器，也可能分别持有采集锁和批次状态。

原因：`media_missher_adapter.py:635` 按 layout.home 放 collection lock；`xhs_policy.py:35` 按 MEDIA_MISSHER_HOME 放风险/间隔状态。此处针对手动配置不同 runtime home 的条件。2026-09-08 升级实施时纠正：当前 Harness 与 Git 默认 runtime 都是 `~/.local/share/media-missher`；早先对 Harness 默认位于 DSH_HOME 的描述不准确。

影响：两个入口同时使用同一浏览器时，可能各自认为可采集，重复工作或破坏统一批次间隔。这里是源码证实的条件性风险，本次没有制造并发去试探平台。

推荐方案：建立可验证、可持续的浏览器身份，由 Git/Harness 共用该身份的采集锁和安全状态；迁移时合并更严格的暂停及最大启动时间，不重置计时。无法确定身份时停止并说明原因，禁止按未知浏览器猜测共享范围。保留现有单安装锁作为保护。

### 优先 2：预检与采集使用同一个版本检查

问题：新 Git 控制器的 preflight 对已安装的旧 15.2.1 报 status=ok，真正进入采集才报“runtime 15.4.0 is required”。

原因：版本门槛在 `media_missher_adapter.py:2160` 的采集入口；`_run_preflight_unlocked` 的 checks 没有 runtime_version。已通过两条 CLI 调用复现，后者在浏览器/输出前停止。

影响：没有绕过安全门，但用户会得到“预检通过却不能采集”的矛盾指引，增加新设备排障成本。

推荐方案：提取同一个只读版本/来源校验，预检和采集共同使用；输出当前版本、所需版本和对应修复入口。不同版本在本地检查阶段直接解释，不自动安装或请求平台。

### 优先 3：阶段进度和耗时

问题：本次采集约 82 秒，但成功运行的 stdout/stderr 没有阶段进度；现有结果主要给总耗时，不能准确拆分登录检查、列表、详情和导出。

原因：核心虽然保存进度快照，Harness processRunner 仍等待完成后解析最终结果；核心没有稳定的分阶段耗时字段。

影响：用户难区分正常等待、平台慢与卡住，也难依据证据挑选性能优化。

推荐方案：增加固定枚举的阶段进度、平台计数和 monotonic 耗时，沿用 committed 快照/现有进程通道；不记录 Cookie、URL 查询串、页面正文或账号标识。先测清耗时，再优化重复本地检查；不缩短 XHS 的保护等待，不提高并发、不新增自动重试。

以上为评估和推荐，本轮没有实施这些新功能；当前 0.4.0 候选及历史归档保持不变。
