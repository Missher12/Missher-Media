## 3. 优先修复的具体问题

以下 P1 表示优先处理的正确性或停止机制问题，不代表已经发生线上封禁、数据泄漏或账户损失。

### F1 · P1：普通内容可能被误判为风险，同时人工维护入口受阻

**问题：** 小红书普通文章提到“风控”，或页面留有隐藏 captcha 节点，都可能触发持久暂停。真实风险写入两份状态后，文档中的人工确认入口又可能无法执行。

**原因：** `platforms/xhs.py:1434` 对整个 body 搜词，并直接接受未检查可见性的验证码节点；相同逻辑在多个详情路径和 `_xhs_detail_enrichment.py:53` 重复。`cli.py:1295` 同时记录小红书和共享风险；`shared_safety.py:208` 会用共享风险阻止普通采集租约，`xhs_policy.py:278` 却先拿这个租约，再执行查询或 acknowledge。

**影响：** 合成正文“今天讨论企业风控系统的设计”触发 `CollectionStopped("风控")`；隐藏 captcha 触发 `challenge-selector`。双风险状态后的真实 acknowledge CLI 退出 78，原因变成 `xhs-safety-state-invalid`，原风险仍存在。共享检查会阻止后续所有平台采集。

**推荐方案：** 复用微博现有的可见阻断容器思路，建立平台可配置的统一检测器，结合可见验证界面、明确风险响应和登录状态；普通文章/评论文字不独立构成风险。状态查询使用只读维护路径；人工确认采用受锁、留审计、失败保持暂停的流程，协调两份状态，保留冷却和其他平台风险。不能只把租约改成 state-only 就结束修复，也不能自动清除风险。

验收：普通正文、隐藏/离屏验证码不误报；真实可见验证弹窗仍停止；双风险状态可读、人工确认可解释且不启动浏览器，其他风险与冷却不丢失。B站/抖音同类全 body 检测一并统一，但本轮误报探针直接验证的是小红书。

### F2 · P1：X 后续翻页出现挑战可能被记成超时

**问题：** X 首次导航有风险检查，后续翻页或等待超时未覆盖同样的检查时机。

**原因：** `platforms/x.py:1019` 后续页只滚动、等待；`1054` 捕获超时后返回 None；`1032` 直接写 timeout。DOM 路径 `1075` 也缺逐页风险检查。

**影响：** 实际 XCollector 配合假 Page 复现：等待结束时 challenge 已出现，结果仍是 `records=[]`、`stop=timeout`。这种状态无法触发原有风险停止链路。

**推荐方案：** 每个主动动作前后、监听超时后复查风险、登录和精确目标；真实挑战优先于 timeout，保存已验证部分结果并停止后续目标。验证码或访问限制不进入自动重试。

验收：首屏、第二页、超时收尾三个时点出现挑战均 risk-stopped；普通慢响应仍 timeout；下一目标不能继续。

### F3 · P1：搜索响应与关键词绑定不完整

**问题：** B站可把另一关键词的已打开页面当成当前请求；抖音监听可能接受另一关键词的旧响应。

**原因：** B站 `platforms/bilibili.py:260-277` 在禁导航时只验域名，随后将记录标成当前 keyword；抖音 `platforms/douyin.py:148-160,429-435` 只按接口路径匹配搜索响应。

**影响：** 探针中 B站页面 `keyword=actual` 被标记为 `requested`；抖音 `keyword=unrelated` 的同接口响应也被 predicate 接受。数据可能归错任务，后续靠重跑无法修正历史归属。

**推荐方案：** 在动作前后绑定规范化关键词、排序、页面/请求来源和本次导航代次；同请求的编码等价可以接受，缺少可核验归属时明确拒收。不要根据帖子内容“看起来相关”推断归属。

### F4 · P1：B站继续搜索会从头导航，首屏去重后可能提前结束

**问题：** 已抓过的首屏会挡住后面尚未抓取的内容。

**原因：** `platforms/bilibili.py:260-261` 忽略 continue_page 而重新导航首页；`270-287` 把历史 ID 和当前页 ID 混用，`added == 0` 就退出；累计 ID 又被传给当前 DOM 变化检测 `1250-1268`。

**影响：** 首屏全部命中排除 ID 的合成用例返回 0 条、滚动 0 次。虚拟列表移除旧卡片时，也可能错误判断页面已经变化。

**推荐方案：** 当前页快照、去重索引和游标分别维护；精确目标一致时保留当前页；用明确结束、游标不前进或有界连续无变化判断停止。首次重复页不应等于内容穷尽。

验收：历史首屏→第二页新内容；固定置顶帖；虚拟 DOM 换页；继续批次不重载首页；所有路径继续服从原页数和时间预算。

### F6 · P2：后续更完整观测被丢弃，统计实体口径可能混淆

**问题：** 当前去重倾向于保留第一条记录，忽略同 ID 后来的补充；B站详情还可能用 null 覆盖先前观测。

**原因：** `best_effort.py:220-230` 对 seen ID 直接跳过；`plan_runner.py:722-739` 只合并目标归属，不合并字段。各平台 append 也存在同类路径。`platforms/bilibili.py:1604-1631` 接受空 stat 后无条件赋值四个指标。

**影响：** 同 ID 先得到 text=null、后得到完整正文，计划结果仍保留 null；B站探针的四个已有值被覆盖为空。**B站动态 module_stat 和视频 stat 属于不同实体的互动口径，不能简单把旧数值填回视频字段。**

**推荐方案：** 保存 `(平台、实体类型、原生 ID、字段、来源、观察时间、精度)`；同实体同字段采用有来源依据的合并规则，缺失不抹去历史观测；动态和视频统计分别保存。利用自然到达的更完整响应，不为合并而补发请求。新采记录数仍按唯一 ID 计算。

### F7 · P2：批次数量、跨目标节奏和实际动作预算存在缺口

**问题：** 单次运行顺序执行并不保证不同任务之间有间隔，条数预算也不等于网页动作预算。

**原因与复现：**

- `plan_runner.py:362-380` fixed 模式固定一批，`cli.py:1192-1244` 将总 count 直接变成 batch_limit。合成 plan 设置 batch_records=5、count=100，实际 collector target=100；同配置 best_effort 的 target=5，正常对照通过。fixed 的一批设计是明确现有语义，但与“统一每批上限”的描述不一致，不能认为已受到同等动作约束。
- 三个微博目标、count=1、声明 interval=90，真实 PlanRunner 的 sleep 注入记录为空；批间隔只发生在同一目标的后续批次。共享锁能阻止并发，不能限制锁释放后的连续短任务。
- XHS 有跨运行持久 last_started_at，其他平台主要使用 `batch_policy.py:80-106` 的内存批间隔。
- 微博话题 `weibo_topic.py:598-601,700-740` 可能为每个新作者导航主页；20 个未访问作者会带来最多 20 次主页访问。XHS 10 条详情若都要评论，既有每条最多 3 次滚动还能再产生最多 30 次评论滚动。这些均有局部边界，但没有统一动作账本。

**推荐方案：** 统一所有入口的预算合同，将 count 视为用户所需总量，细分有限批次；持久化按平台和受验证浏览器身份的动作准入时间，跨目标、跨任务、跨 Agent 共用。导航、翻页、开详情、评论滚动、主页访问分别计费，失败尝试也计费；保留单浏览器所有权。确需改变 fixed 单批合同，应版本化并明确 partial/budget-exhausted 语义。

### F8 · P2：计划中的必需字段没有落实为采集完成条件

**问题：** CollectionPlan 已有 required_fields/field_groups，但采集执行链没有消费它们。

**证据：** `contracts.py:325-326,419-420` 保存字段；`cli.py:1188,1231-1248` 没有按字段规划，`686-691` 只检查截图和 complete。实际 PlanExecutor + 合成 dispatcher 返回缺 text 的记录，即使 plan 要求 text，仍得到 complete。DSH `harness-plugin/src/plan.ts:103-104` 当前固定写空数组，故不能说默认 DSH 用户已经传入并丢失了这一要求。

**推荐方案：** 让字段合同进入完成判断和访问计划。缺必需字段返回 partial + 明确缺失原因；列表足够时不打开详情，只有用户所需字段确实缺失且预算允许时才做授权补充。先定义公共能力，再统一 Python/CLI/DSH 参数，不能只加一个 UI 开关。

## 4. 有实质收益的增强方案

### A. 跨任务的持久访问节奏与动作预算

在现有共享锁内增加原子预算预留和结果记账，不引入第二套浏览器所有者。以已验证浏览器身份和平台绑定状态，不依靠临时任务 ID 重置；进程内用单调时钟，持久时间校验未来值与时钟回拨。配置只能收紧已有保守基线，不能把本地 60/90/120/600 秒当作平台官方安全阈值。

已捕获的 429 保持立即停止；记录合法 Retry-After 的秒数/日期，供诊断和**人工确认后的最早准入时间**使用，不自动清除风险或重试。429 语义见 [RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)，Retry-After 两种格式见 [RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after)。没有响应头时不能自行推断已恢复安全。

验收重点：两个 Agent 先后发起短任务仍共用预算；进程崩溃不退回已消耗动作；跨目标不突发；长等待不越过总截止时间；风险停止不进入自动恢复。

### B. 跨运行增量索引与字段新鲜度

当前有同运行去重和显式精确计划恢复（`cli.py:1369`），不是通用的跨运行增量抓取。建议新增本地索引，绑定目标、原生 ID、内容摘要、来源和观察时间。

- 稳定内容和经验证的旧详情可以复用，并标明历史来源；点赞等易变指标单独保存新观测。
- 用户明确选择“更新指标”“只找新增”“补齐所需字段”，决定是否需要访问。
- 增量列表保留小范围重叠窗口，处理置顶、乱序、编辑和删除；遇到第一条旧记录不立即停。
- 旧记录不能计入“本次新抓取条数”，读取历史不得冒充最新平台状态。恢复仍拒绝风险停止任务，不绕过预算。

可量化目标是第二次同目标任务的重复导航和详情打开次数下降；具体比例必须由受控基准测量。

### C. 按需补详情，保留主列表位置

把摘要、详情、评论、作者主页分成可核验成本的工作项，优先满足 required_fields。主页/详情对同一实体同一新鲜度窗口只访问一次。B站完整模式应保留列表滚动位置，再顺序处理一个受控详情页，避免视频详情后又回首页寻找深页动态（`bilibili.py:181-220,295-298`）。所有临时页继续沿用 DetailOpenCoordinator 的精确归属与清理。

验收：三页列表中先视频后深页动态，目标不串、列表不反复重载；只要摘要时详情导航为 0；评论数量和预算不会被详情补充偷偷扩大。后者是拟定验收目标，不是本轮已实现状态。

### D. 有界响应队列与事件就绪判断

在当前任务开始时监听网页已产生的匹配响应，按目标、请求代次、实体和游标去重，短期保存在有大小/时间上限的内存队列。先消费已收到的有效页，再决定是否滚动。仍由网页自身正常动作发请求，不重放登录令牌或自行构造站内私有接口请求。

这是在现有一次动作只等一份响应的基础上研究利用率，并非本轮已证明所有平台必然丢响应。实现前用“一个动作产生两个响应、旧页晚到、目标切换、超时后晚到”的回放用例验证。

加载完成用精确响应/DOM 条件和有界截止时间判断；**保留访问节奏用的等待**，不要把删除固定加载等待误解成取消限速。[Playwright 网络事件](https://playwright.dev/python/docs/network)支持响应匹配与等待；[Page 文档](https://playwright.dev/python/docs/api/class-page#page-wait-for-timeout)建议以事件和可见条件代替猜测加载所需时间。

### E. 浏览器兼容矩阵与更可解释的结果

`runtime/requirements.lock` 固定 Playwright 1.45.0；浏览器通过 CDP 外连，版本可能独立更新。应记录 Chrome/Playwright/运行核心构建身份并用本地 fixture 验证，不直接把升级依赖等同于降低风控。现有专用 user-data-dir、loopback 端口和持久登录会话设计可保留。[Playwright 官方文档](https://playwright.dev/python/docs/api/class-browsertype#browser-type-connect-over-cdp)说明 CDP 的功能覆盖与 Playwright 原生连接不同；[Chrome 官方说明](https://developer.chrome.com/blog/remote-debugging-port)要求 Chrome 136 起默认数据目录之外的独立目录用于远程调试。

每次结果新增低敏感运行摘要：列表响应数、有效新 ID 数、重复 ID 数、详情/主页/评论动作数、来源覆盖、缺失字段、风险分类、停止原因。只保存白名单诊断，不把 Cookie、Authorization、完整原始页面或登录信息写入日志。由这些指标定位需要优化的路径，不能只以总抓取条数评价效率。

## 5. 建议实施顺序和验收门槛

| 阶段 | 交付 | 必须通过的证据 |
| --- | --- | --- |
| 第一批：正确性修复 | F1–F5：风险误报/漏报、受锁维护、搜索绑定、增量分页、计数与响应结构 | 每个本轮失败探针转成回归；真实风险仍停；错误数据不进成功结果；保持既有 505 项覆盖 |
| 第二批：统一预算 | F7、持久动作账本、跨目标/任务节奏、Retry-After 诊断 | 多入口/多进程交替、崩溃、时钟异常、取消与截止时间；真实请求数量不能绕过账本 |
| 第三批：有效信息复用 | F6/F8、按字段规划、增量索引、受控详情页、响应队列 | 同实体来源一致、历史与新鲜分开、重复动作下降、字段完整性增加；保持旧历史可读 |
| 第四批：现场小样本 | 修复后的精确候选和少量已授权平台目标 | 每个平台单独记录新 ID、动作数、字段覆盖、误停/漏停和停止原因；出现挑战立即结束，不扩大样本 |

本轮没有产生安装候选，因此没有跨过宿主日常安装的单一写入者安排，也没有为研究改变私有仓库可见性。第一批无需更换 CDP 后端；后续方案仍可在现有共享核心内实现。

评价指标建议采用：每个新记录所需动作数、重复动作率、必需字段有效覆盖率、错误归属数、误停数、挑战出现后继续动作数、可解释 partial 比例。对于相同离线回放，正确性修复应先做到错误归属/错误数值/遗漏已在响应中的记录不增加；对真实平台，成功率与触发频次需要另行现场验证，不能由静态审查或这些测试推算。
